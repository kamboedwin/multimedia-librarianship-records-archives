Multimedia Publishing, Evaluation and Applied Project

Integrating production, accessible access, metadata, responsible release, usability evaluation and professional presentation.

← Back to Unit 12 on the course site

Start here: a familiar situation

A student team has built a digital collection with attractive images, a video and a search box. Before publishing, they ask whether visitors can find an item, whether the sources are identified, whether the video has captions, whether publication is authorised and whether files can be maintained. A successful multimedia project is judged by real user tasks and responsible management, not appearance alone.

Key words in simple language

  • Publishing: making a resource available to its intended audience.
  • Usability: how effectively and easily users can complete tasks.
  • Evaluation: collecting evidence about whether a resource meets its goals.
  • Release readiness: the documented result of checking a product before publication.

Think about it: Can a beautiful website be unsuccessful if users cannot find the information they need? The sections below explain how to answer this question.

For other terms, see the course multimedia glossary.

Learning outcomes. Plan an integrated multimedia information service; build a responsibly published prototype; document a media inventory and metadata; test accessibility and usability; analyse task-completion evidence; prioritise fixes; and present a defensible BLISS or BRIM project.

12.1 Multimedia publishing is a professional service

A multimedia product joins different forms of information such as written text, still images, sound, moving images and interactive controls. A professional multimedia service does more than display those elements attractively: it helps a defined audience complete a task. In a library, the task may be locating a digital exhibition or understanding how to access electronic resources. In a records or archives environment, it may be identifying the correct record series, understanding provenance and knowing whether a digitised item may lawfully be viewed.

The complete workflow moves through problem identification, planning, content preparation, authoring, description, preservation, rights checking, accessible publishing and evaluation. Each stage provides evidence for the next stage. For example, a public item page cannot be evaluated properly if the metadata does not identify the item or the video has no accessible alternative.

The final unit integrates the skills gained in the previous eleven units. It uses a small capstone project to demonstrate that students can apply, not merely define, the main multimedia concepts. A project that looks attractive but fails a basic retrieval task is incomplete. A project that publishes a restricted interview without adequate authorisation is also incomplete.

12.2 Defining the problem, audience and outcomes

A project begins with a specific problem statement. “We will create a website” describes a technology choice, not a problem. “New library users cannot find the guide to online catalogues on their phones” identifies users, a task and a barrier. A parallel archives case is that external researchers cannot tell which collection descriptions can be browsed without special permission. Defining the problem this way guides content selection, navigation and evaluation.

Audience analysis considers prior knowledge, access needs, preferred language, digital literacy, device, internet availability and likely context of use. Students should not assume everyone uses a large laptop and fast data connection. A mobile visitor may need a short transcript instead of a large streaming video. A keyboard-only user must be able to operate every essential control, while a researcher needs identifiers and source context.

Scope protects project feasibility. A useful minimum prototype might have a home page, a browse page, three item records, one audio/video alternative and a clear help/access page. State measurable success criteria: for example, all three sample items have correct identifiers, all navigation links work, and at least one representative user can complete a documented search task without direct assistance. These criteria guide tests rather than promising a universal outcome.

12.3 Planning the media inventory and production workflow

A media inventory is a structured list of every image, recording, caption, transcript and visual asset used by the project. It records an identifier, title, source or creator, intended use, file type, location, status, rights basis, alt-text/transcript needs and whether the file is an original or derivative. The inventory prevents an apparently completed website from containing unexplained or unauthorised material.

For an archival scan, a controlled higher-quality original can coexist with a smaller publicly accessible viewing copy. The relationship should be documented. For audio, a retained recording may have a compressed listening derivative and a reviewed transcript. Transformations should preserve enough information for users to understand what the resource contains; cropping, filtering or transcription errors can otherwise change the interpretation.

Build a realistic workflow: select media, inspect rights and privacy, check quality, produce derivatives, write accessible alternatives, enter metadata, link files to records, test retrieval and record release approval. When AI assistance is used, distinguish unverified generated suggestions from verified catalogue facts and avoid sending restricted material to unauthorised tools.

12.4 Information architecture and interactive design

Information architecture describes how content is grouped, labelled and connected. A small project can use Home, Browse Collections, Item Details, About and Help as its principal pages. Navigation labels should describe destinations. “View restricted access guidance” is more informative than an ambiguous “Click here”. Every item page needs a predictable path back to Browse and a visible identifier for citation or correspondence.

An interactive design should be purposeful. A search box is useful when it searches actual item titles, descriptions or subjects and explains when no matches are found. A carousel that automatically moves before users finish reading may obstruct access. Interaction should support the audience task, work on touch screens and remain usable without a pointing device.

A storyboard sketches the intended route before implementation. Imagine a library learner opening Home, selecting Browse, using a “study skills” subject filter, reading an item and opening its audio explanation with a transcript. In an archival guide, an equivalent route must distinguish the public item description from any restricted original file. These routes become evaluation test cases.

12.5 Metadata and discoverability

Metadata gives a media object context and helps users find and interpret it. A core record may include identifier, title, creator or originating body, date, media type, subject, description, rights, source and any collection relationship. The Dublin Core terms provide widely understood names for many descriptive fields, but a local application must define which fields are mandatory and what values are valid.

Identifiers should be unique within the collection and stable across internal file renames. An identifier such as LIB-001 or ARC-003 can connect the public item page to its media inventory and source documentation. For a series of archival records, describe provenance and relations between a record and its collection rather than flattening everything into isolated photographs.

Retrieval quality can be explored using realistic search tasks. Test alternate terms, empty results and ambiguous phrases, and review whether titles expose protected personal information. A search system is not successful simply because it returns something; users need relevant, intelligible and authorised results.

12.6 Accessible media and inclusive use

Accessibility should be designed and tested throughout the project. Informative images need text alternatives that communicate their purpose. A recorded interview should have a checked transcript, and synchronised captions should convey meaningful speech and sounds when it appears in video. Important visual information that cannot be understood from existing narration may also need description. These choices help users with different sensory needs and often improve access on low-bandwidth devices.

Interactive elements should be reachable by keyboard, have visible focus and meaningful labels, and appear in a sensible reading order. Text should remain readable at increased zoom and within narrow mobile layouts. Colour alone should not be the only way to identify a problem or essential action. Automated testing can discover some defects, but W3C guidance makes clear that knowledgeable human review is still needed.

An accessibility test log records what was tested, by whom, on which device or browser, the result, the defect and the retest. An accessible interface is not demonstrated by a sentence in the report saying “the site meets WCAG”; it requires evidence that relevant tasks can actually be completed.

12.7 Rights, privacy and ethical release

Before public release, review each asset for copyright, permitted reuse, personal information, consent scope, institutional authorisation and the possibility of misrepresenting people or events. Possessing a photograph or scan does not automatically give the right to publish it. A public institution may preserve an item for legitimate purposes while limiting online access. A description of a restricted item may be safer than a link to the item itself.

A rights and access register should state the item, known creator or rights holder, evidence, intended publication, conditions, restrictions, status and responsible reviewer. When material is uncertain, the proper status may be “restricted pending review” rather than “free to use”. Fictional course materials avoid asking students to upload real confidential records or identifiable interviewees into a public learning platform.

Ethical review also covers representation. Do not invent a person’s identity or a historical date merely because an AI tool produces a convincing result. Preserve context, label synthetic representations, and explain uncertainty. The aim is a resource that is respectful, traceable and useful to its intended audience.

12.8 Quality assurance, quality control and release readiness

Quality assurance is the planned process used to reduce defects. It might require a naming convention, a metadata template, peer checking and a standard file-export procedure. Quality control examines the output: does the media open, is the caption accurate, are links correct, are filenames safe, do the display images look acceptable, and does each record have the required fields?

A release checklist should examine content accuracy, rights and privacy, source–derivative relationships, accessibility, navigation, mobile responsiveness, search, media playback, metadata, backups and responsibility for later corrections. A completed checklist is meaningful only when it refers to verifiable evidence. For example, “keyboard tested on 12 November; all main links reachable; one tab-order issue repaired” is better evidence than an unexplained check mark.

The release decision should separate critical blockers from improvements that can be scheduled. A leaked private record, missing permission for published media or inaccessible core navigation is a critical issue. A small spacing inconsistency may be logged for later improvement. Decisions and exceptions must be documented and approved by the relevant responsible person.

12.9 Evaluating usability and interpreting results

Usability evaluation examines whether people can perform meaningful tasks. A simple teaching protocol defines a task and starting page, asks a representative participant to attempt it without coaching, and records observed completion, time, assistance, errors and comments. Example task: “Find the public description of photograph LIB-002 and identify how you would cite it.” Another task might ask an archival user to determine how to request access to a restricted interview.

A basic completion rate is calculated by dividing the number of successful valid attempts by the number of valid attempts, then multiplying by 100. If 8 of 10 attempts succeed, the observed completion rate is 80%. Suppose task times in seconds are 30, 45, 41, 60 and 55. The median is 45 seconds when arranged in ascending order (30, 41, 45, 55, 60). Time should be compared only with consistent tasks and conditions, and usually interpreted alongside observed difficulties.

A small classroom sample is useful for locating usability problems but cannot establish a population-wide success rate. A participant may complete a task only after significant backtracking. Report the small sample size, criteria for success and limitations. A useful evaluation combines task observations with clear, actionable repairs rather than only an average score or satisfaction statement.

Worked result: 8 successful attempts ÷ 10 valid attempts × 100 = 80% observed task completion. With times 30, 41, 45, 55, 60 seconds, the median is 45 seconds. The numerator, denominator and testing context must be reported.

12.10 Acting on test results and improving the product

Turn every important observation into an issue record: short problem description, affected task, severity, evidence, proposed change, owner, status and retest outcome. Examples include a broken “Back to Browse” link, an inaccessible audio player, a search result that hides key rights conditions and a label that incorrectly says an interview is publicly downloadable.

Prioritisation may consider impact and implementation effort, but safety, privacy and access blockers take precedence. A high-impact, low-effort fix such as correcting a broken link should be handled rapidly. A complex redesign may need scope control and a documented plan. A cosmetic improvement should not consume the resources needed to fix essential access failures.

After a change, repeat the affected task and preserve both the original observation and the new evidence. A change log might read: “v0.2: added transcript link to Item 2; keyboard retest completed; pass.” Versioning is part of transparent practice, not merely software development administration.

12.11 Publishing on a static website and maintaining it

A small multimedia resource can be published as a static site: a top-level index.html, styles, scripts, media, catalogue data and supporting documentation. Static hosting is suitable for public, non-sensitive educational outputs. GitHub Pages has case-sensitive file paths and public deployment implications. Students should never place passwords, identifiable interview details, restricted source files or lecturer-only marking guides in a publicly accessible repository.

Test the same folder structure locally before upload. Ensure every link is relative or points to the intended official resource; verify that sample data, captions, images and downloadable reports open after publishing. The README should identify the project, audience, authorship, how to navigate it, sample-data limitations, rights and version information.

Publication is not a one-time event. Assign responsibility for correcting inaccurate catalogue descriptions, repairing broken links, reviewing rights restrictions and keeping the accessible content usable. Preserve an authorised source set separately, maintain a checked backup and record important revisions.

12.12 The applied capstone: BLISS and BRIM

The BLISS option is an interactive library orientation or miniature digital exhibition containing at least three properly described items. It must offer a readable introductory page, a usable browse path, media content, accessible alternatives, relevant rights records and documented tests. The professional goal may be introducing new readers to services, or helping the public discover a small themed collection.

The BRIM option is a fictional archive or records-access portal with at least three described records. Students must express provenance and collection relationships, clearly identify any restricted item, avoid publishing that item and explain an authorised access request route. The project should preserve source and derivative distinctions and show how digitisation, metadata and access policy fit together.

For both options, the project portfolio contains a problem statement, target audience, sitemap, media inventory, working prototype, metadata, rights/access decisions, accessibility test log, usability protocol and results, issue/fix log and a brief demonstration. A 100-mark instructional rubric can be scaled to 20 marks if the relevant assessment rules require it. Neither scale is automatically an official mark allocation.

12.13 Final presentation and reflective evaluation

An effective final demonstration begins with the problem and intended users, then shows a complete user task rather than a tour of menus. The student should explain one significant design decision, demonstrate accessible media or metadata retrieval, and present at least one test observation that led to an improvement. The final slide may summarise what works, what remains limited and what would be improved next.

Reflection should not merely say the project was successful. It should identify evidence: which tasks participants could complete, which defects were corrected, what access decision protected an item and how the project could be maintained. This teaches critical judgement and gives future MSc or professional project work a reproducible structure.

The full course progression is now connected: multimedia fundamentals and creation, compression and delivery, authoring and interaction, digitisation, metadata, preservation, ethical publication and evidence-based evaluation. The final goal is a useful, responsibly managed and continuously improvable information resource.
