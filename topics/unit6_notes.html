File Formats, Compression and Delivery

Selecting, calculating, verifying and delivering useful multimedia files in libraries, records offices and archives.

← Back to Unit 6 on the course site

Start here: a familiar situation

A digital exhibition has a large image, a five-minute interview and a demonstration video. Visitors on mobile data may find the files slow or expensive to open. Publishing smaller access copies can make the service usable, but the institution still needs trustworthy retained versions. The correct choice depends on the information being preserved and the network and devices used for access.

Key words in simple language

  • File format: a specification for how digital information is arranged and stored.
  • Compression: representing data with fewer bits.
  • Lossy compression: size reduction that discards some information.
  • Bitrate: the amount of encoded media data used per second.

Think about it: Why can the smallest file be the wrong choice for an archive? The sections below explain how to answer this question.

For other terms, see the course multimedia glossary.

6.1 Learning outcomes and the professional problem

By the end of this unit you should be able to identify file formats and media encoding properties; distinguish lossless and lossy compression; calculate raw and bitrate-based file sizes, compression ratios and ideal transfer times; choose formats suited to different information-service purposes; document a source-to-access workflow; and evaluate practical delivery for users with different devices and network conditions.

Consider an institutional digital collection containing poster photographs, oral-history recordings and a short orientation video. Staff want to preserve the collection responsibly, while students want quick, reliable access on mobile phones. Uploading the largest files without considering users wastes data and can make the service unusable. Keeping only highly compressed delivery copies, however, may prevent future editing, quality inspection or long-term reuse. The task is therefore to make purpose-specific choices, not to find a universally perfect format.

Guiding question: Which version of a resource should be retained under institutional control, and which version is safe and practical to deliver to the user?

6.2 Digital file formats and technical vocabulary

A file format is an agreed structure for representing information as bytes. The structure allows suitable software to interpret data, such as pixels in an image, samples in an audio recording or pages in a document. A filename extension such as .jpg or .mp4 is a human-readable clue to the intended file type; it is not proof of the internal contents. Renaming document.jpg to document.png does not convert its JPEG encoding into PNG.

A codec is an encoder/decoder: a set of methods for representing and reconstructing audio or video information. A container is the file structure that packages one or more media streams and related metadata. An MP4 container can hold H.264 video with AAC audio, for example. MIME/media types such as image/jpeg, audio/mpeg and video/mp4 are labels that help software and web browsers handle resources. An MP4 extension by itself does not reveal the exact codecs, profiles or compatibility of every stream.

Example: A BLISS teaching video is named catalogue_guide_access.mp4. You inspect the file and discover an MP4 container with H.264 video, AAC audio, 1280 × 720 pixels, 25 frames per second, and an average combined bitrate near 1.5 Mb/s. Those properties describe the file more usefully than the filename alone. If a BRIM department receives an unexplained .mov file, staff should identify its actual streams before assuming it will play or remain usable in a particular workflow.

6.3 Image, audio and video formats: a purpose-based comparison

Images. PNG uses lossless image compression and can represent transparency; it is useful for screenshots, diagrams and graphics with fine edges. JPEG uses generally lossy photographic compression and can be an efficient access format for photographs. TIFF is a flexible raster format that can contain uncompressed or compressed image data and extensive technical information; a TIFF extension does not prove it is always uncompressed or suitable for every preservation policy. SVG stores vector shapes, text and coordinates and is useful for scalable diagrams; it is not a replacement for all photographic imagery.

Audio. WAV commonly stores linear pulse-code-modulation (PCM) samples and may be used for controlled source recording. Broadcast WAVE can carry useful embedded metadata. FLAC compresses audio losslessly, so the decoded samples are retained, subject to the encoding process and file integrity. MP3, AAC and Opus are common lossy choices for listening or web delivery. A five-minute spoken guide rarely requires the same quality and channel count as a professionally mastered music recording; consider speech intelligibility, file size and device support.

Video. MP4 is a widely used container. H.264 video plus AAC audio is a practical broadly supported access combination. WebM supports formats such as VP9/AV1 video and Opus audio; support and performance depend on target browsers and hardware. High-quality retained video may follow different specifications from a compressed public access MP4. The appropriate choice depends on original acquisition, editing needs, rights, institutional policy and long-term management resources.

6.4 Why compress files?

Compression is a method for representing information with fewer bits. Smaller files may reduce storage requirements, upload time, mobile data use and network load. Compression methods work because some information is predictable or redundant; for media, encoders may also exploit characteristics of human vision and hearing. Compression is not always beneficial for every input: a previously compressed file may become very little smaller when placed into a ZIP archive.

Lossless compression reconstructs the original decoded information exactly according to the format. PNG and FLAC are common examples. A ZIP archive also normally allows exact recovery of the stored bytes. Lossless does not mean the file is uncompressed, automatically authentic or guaranteed future-proof.

Lossy compression discards or approximates some information to reduce size. Ordinary JPEG images, MP3 recordings and many H.264 video encodes are lossy. At sensible settings, a user may find them suitable for the intended task; at aggressive settings, important information can be damaged. Examples include blurred handwritten names in an archival photograph, ringing around printed letters, metallic speech or smeared movement in a video tutorial. Once information is removed by lossy coding, merely renaming the file or increasing its pixel dimensions cannot restore it.

There is an important distinction between visually acceptable access and bitwise preservation. An access copy may look sufficiently clear while still differing from the source at the pixel or sample level. Conversely, a lossless file may still be unsuitable if the underlying capture was out of focus or poorly exposed.

6.5 Compression ratio and percentage saved

For a source file of S units and an output file of C units, two useful measurements are:

Compression ratio = S ÷ C
Percentage saving = ((S − C) ÷ S) × 100%

Worked example: A scan is 80 MB before compression and the access copy is 20 MB. The ratio is 80 ÷ 20 = 4:1. The saving is ((80 − 20) ÷ 80) × 100 = 75%. This calculation measures size reduction; it does not tell us whether small text remains readable, whether authenticity was affected or whether the new copy is approved for public access.

A file that grows from 10 MB to 11 MB after conversion has a ratio below 1 and a negative “saving”. This is possible if the input was already efficiently encoded or the output includes more data or metadata. Report the actual measured file sizes and encoding settings.

6.6 Units of digital storage and network speed

A bit is one binary digit; a byte contains eight bits. Network speed is often given in megabits per second (Mb/s), while files are typically described in megabytes (MB). The uppercase B matters: 8 Mb is only 1 MB under decimal conventions. In decimal units, 1 MB = 1,000,000 bytes and 1 Mb = 1,000,000 bits. Binary units have different values: 1 MiB = 1,048,576 bytes and 1 GiB = 1,073,741,824 bytes.

When writing calculations, specify whether you are using decimal MB or binary MiB. Do not silently combine them. For example, 11,520,000 bytes = 11.52 MB or about 10.99 MiB. Both are descriptions of the same byte count with different units.

6.7 Estimating uncompressed raster image storage

For a simple packed uncompressed raster image without row padding, file header or metadata:

Raw image bytes ≈ width × height × bits per pixel ÷ 8

Example: An image is 2400 × 1600 pixels at 24 bits per pixel (e.g. 8 bits per channel × 3 colour channels). Its raw pixel count is 3,840,000. Its raw storage is 3,840,000 × 24 ÷ 8 = 11,520,000 bytes or 11.52 MB. The actual file may be smaller or larger because format-specific compression, headers, metadata and other components vary.

Do not confuse the number of pixels with pixels-per-inch (PPI). PPI contributes to the planned physical representation, but the file-size baseline above depends directly on actual pixel dimensions and bit depth. Colour space, alpha channels and higher precision also matter.

6.8 Estimating uncompressed PCM audio storage

For simple uncompressed PCM audio without a container header:

Raw audio bytes ≈ sample rate × bit depth × channels × duration ÷ 8

Example: A 60-second stereo recording at 48,000 samples/second and 16 bits/sample has 48,000 × 16 × 2 × 60 ÷ 8 = 11,520,000 bytes (11.52 MB). The same recording captured as mono has about half that raw sample data. A compressed MP3 copy cannot be estimated from sample rate and bit depth alone because its encoded bitrate controls storage much more directly.

Choosing settings must consider purpose. Speech recorded for quick access can be delivered at a much smaller encoded bitrate than a controlled source recording. For oral history, staff should also record interview consent, source context, language, any restrictions and transcription status. These details cannot be replaced by an audio file-size calculation.

6.9 Estimating compressed audio/video size from bitrate

When average bitrate is known, a first approximation is:

File size (MB) ≈ total average bitrate (Mb/s) × duration (s) ÷ 8

Example: A tutorial uses about 2.5 Mb/s video and 128 kb/s audio. Convert audio to 0.128 Mb/s, then total = 2.628 Mb/s. For 180 seconds, estimated size = 2.628 × 180 ÷ 8 = 59.13 MB (about 56.39 MiB). This ignores small container overhead and assumes the stated average bitrate holds. A real file with variable bitrate, extra tracks or metadata can differ.

Two files at the same bitrate may not look or sound equally good: efficiency differs by codec, settings, scene movement, colour detail, sound complexity and the player/device. A higher bitrate also does not repair poor original recording. Always test actual outputs.

6.10 Bandwidth, transfer time and access choices

Given a file size in decimal megabytes and a sustainable throughput in megabits per second, the ideal transfer time is:

Ideal transfer seconds ≈ file size (MB) × 8 ÷ throughput (Mb/s)

Example: A 40 MB file on a hypothetical 2 Mb/s connection needs 40 × 8 ÷ 2 = 160 seconds, or 2 minutes 40 seconds, assuming continuous full throughput. Actual transfers can take longer because networks share capacity, connections fluctuate, protocols add overhead and clients may experience retries or throttling. The time is a planning estimate, not a guarantee.

Low-bandwidth delivery is important for a public or student-facing service. Prefer readable pages, do not autoplay large media, display approximate download sizes, provide concise access renditions and offer transcripts, captions, descriptive alternatives or static illustrated instructions where they meet the same learning need. Check playback and downloading on a representative phone, not only on a powerful office computer.

6.11 Progressive delivery and streaming

Progressive download allows a browser to receive a standard file and often begin playing before the entire download is finished. A simple HTML5 <video> or <audio> element can support this without a specialised streaming platform. Adaptive streaming typically supplies multiple renditions or segments that can be selected according to conditions; it can improve the experience for large or widely used media libraries, but adds production, hosting and testing complexity.

For a small static multimedia website, one practical approach is a correctly encoded media file, an explicit download option, captions and a transcript. Avoid assuming that an .mp4 extension guarantees playback across every browser, profile or device. Provide and test alternatives when needed, and label media with appropriate MIME types.

6.12 Source, working and access versions

Professional workflows commonly maintain more than one version of an information resource. The controlled source/master is acquired or produced according to the institution's quality and custody policy. A working/mezzanine copy may support editing, correction and export. An access derivative is prepared for practical delivery, such as an appropriately sized JPEG, MP3 or MP4. Master does not automatically mean “TIFF for every image” or “WAV for every sound”: retention requirements vary, and original formats may also need to be kept.

A managed collection should record which file comes from which source, when a transformation occurred, its settings, who performed it, the access restrictions, and what was checked. A file manifest might include item_id, filename, role, media_type, bytes, dimensions_or_duration, codec, rights and derived_from. A checksum, for example SHA-256, helps confirm whether a known file's bytes changed; by itself it does not authenticate the truth of the content or the authority of the creator.

Repeated lossy export: Avoid editing by repeatedly recompressing the only JPEG or MP3 you have. Keep a controlled original and generate new copies from a suitable source. If a derivative is redacted, document the authorisation and retain source controls. Never treat an apparently blurred or hidden personal record as safe without checking all audio, metadata and contextual clues.

6.13 Format sustainability and professional judgement

Consider a format's documentation, disclosure, adoption, software availability, metadata support, intellectual-property dependencies and ability to migrate. The Library of Congress Recommended Formats Statement is useful for understanding professional factors, but it is not an institutional policy document and is principally oriented to acquisition of published works. The MDN video codec guide is a helpful technical reference for web compatibility; actual device testing remains essential.

Preservation is an ongoing management activity: monitor software dependencies, keep technical metadata, maintain integrity checks, review format risks and plan for future transformations with quality verification. A widely used access codec may be the correct choice for today's users while a different source format must be retained for future work.

6.14 Worked BLISS and BRIM cases

BLISS: digital library resource pack

A library wants to publish an exhibition photograph with small printed labels, a three-minute tutorial video and a short voice guide. The public audience includes students using phones with limited data. The team keeps controlled source images and recordings, evaluates JPEG/PNG derivatives for visible text, produces a captioned and tested MP4 tutorial, and provides the spoken instructions as a transcript. A manifest links each derivative to its source. The library tests whether students can read the labels and complete the taught catalogue task.

BRIM: fictional archival access pack

An archive wants to share selected authorised photographs and an oral-history excerpt. The team keeps approved originals under access control, records provenance and permissions, makes redacted access derivatives where authorised, and checks whether dates, names or evidence were altered. Download and streaming copies are named and documented separately from controlled masters. For classroom exercises, use only the supplied synthetic files; never upload actual confidential records to a public repository.

6.15 Guided practical experiment

  1. Inspect the resources. Download the supplied synthetic image variants. Open each file and record its real dimensions, format, byte size and visual differences, particularly around small labels.
  2. Calculate compression. Compare the same-source PNG and JPEG versions using their measured bytes. Find the ratio and percentage saving. Decide whether the most compressed version still supports the intended information task.
  3. Estimate raw storage. Apply the image formula using width, height and 24 bpp, noting the difference between theoretical raw data and actual encoded file size.
  4. Compare audio. Listen to the Unit 4 narration WAV and MP3. Record measured byte sizes and whether speech remains clear on headphones and an ordinary phone. Do not treat a subjective impression as a scientific blind test.
  5. Plan video delivery. Inspect the synthetic Unit 5 video. Estimate a hypothetical three-minute access file using 2.5 Mb/s video and 128 kb/s audio; calculate ideal download time at 2 Mb/s.
  6. Make a decision. Prepare a simple format-decision matrix for BLISS or BRIM, distinguishing source, working and access roles. Include rights, captions/transcripts, a file manifest and at least two validation checks.

Use the downloadable laboratory worksheet and manifest CSV template. You may use an image editor for a controlled same-source export to compare quality settings, but the website's interactive controls are educational simulations/calculators; they do not transcode your own media files.

6.16 Common mistakes and a final checklist

  • Calling MP4 a codec or assuming every file with a .mp4 extension has the same video and audio streams.
  • Reporting 8 Mb as equal to 8 MB; mixing MiB and MB without conversion.
  • Presenting a theoretical raw image size as if it were a real JPEG file size.
  • Assuming every lossless file is necessarily the best archival master or that every small access derivative is acceptable.
  • Using compression ratio as proof of image accuracy or archival authenticity.
  • Giving a network transfer estimate without acknowledging overhead and variable speeds.
  • Publishing the only copy of a record, omitting rights checks, captions or file relationships.
Takeaway: Decide what must be faithfully retained, what users really need, what their devices can play, what they can afford to download, and how every file will be validated and documented. Media files become much more useful when they are connected through clear navigation and multimedia authoring.
