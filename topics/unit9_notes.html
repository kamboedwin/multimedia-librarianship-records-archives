LIU08106 / RIU08106 · Unit 09

Multimedia Metadata, Organisation and Retrieval

Describe resources consistently, connect their context and help the right users find them safely.

Start here: a familiar situation

A photograph named IMG_0048.jpg may be perfectly clear, yet nobody can find it by searching for the event it shows. A catalogue record can supply a meaningful title, date, creator, subject, source collection and access status. Metadata connects a file to its identity and context; organisation and consistent terms help users retrieve it.

Key words in simple language

  • Metadata: structured information describing or managing another information resource.
  • Identifier: a stable code or value used to distinguish an item.
  • Controlled vocabulary: an agreed set of terms used consistently for description.
  • Provenance: information about the source and history of an item.

Think about it: Why is a filename alone rarely enough for reliable discovery? The sections below explain how to answer this question.

For other terms, see the course multimedia glossary.

Learning outcomes. By the end of the unit you should classify metadata, create Dublin Core-based records, connect source and derivative files, design controlled terms and identifiers, assess metadata quality, and test retrieval in a small BLISS/BRIM collection.

Metadata is not merely a list of technical properties. It gives a digital item an identity, an interpretation, a management context and rules governing its use. The most useful records are sufficiently accurate for someone who did not create the file to locate, understand and use it. In this unit you will learn both a general framework and a practical collection workflow. All exercises use fabricated resources, not real private student or institutional records.

9.1 Purpose and kinds of metadata

Why multimedia needs metadata

An image filename does not tell a user who created the image, when it was made or whether public use is permitted.

Audio needs recording context, participants or roles, transcript availability, language and rights.

Video needs title, creator, duration, captions, subject, access conditions and technical details.

Applied explanation. A photograph taken during a library event might be saved as IMG_4821.jpg. From that filename alone, a search user cannot reliably tell which event it depicts, its date, its creator, the location, what licence is available or the relationship to an exhibition. A descriptive catalogue record can answer these questions, while technical metadata can document capture properties. The ability to search a file on a computer does not mean users can make sense of it.

Key point: Metadata turns an isolated file into a resource that can be managed and found.

Data, information, content and metadata

Content is the resource itself—for example, the pixels of a photograph or samples in a WAV file.

Metadata is structured information about that content, its context, use, technical properties or lifecycle.

Metadata can be embedded in a file, stored in a catalogue database, linked in a manifest or kept in a preservation log.

Key point: Do not assume all metadata is embedded in the media file.

Five practical categories of metadata

Descriptive: title, creator, subject, description and dates for discovery.

Structural: sequence, part–whole links, page order and relationships between master and derivative.

Technical: format, dimensions, duration and codec; administrative: ownership and access; preservation: fixity and events.

Applied explanation. The categories are useful for planning but they are not watertight compartments. For example, a file format may be useful in access selection and in preservation planning. A series identifier supports both structural description and records administration. Name the purpose for which each piece of information is collected.

Key point: One field can support several purposes; these categories overlap.

Descriptive metadata in practice

A meaningful title identifies the resource: “Student orientation guide”, not “final_video2”.

Creator identifies responsible person or organisation; subject terms express what the resource concerns.

Language, date, description and relevant geographic coverage improve filtering and interpretation.

Key point: Describe the resource faithfully, using evidence rather than assumptions.

Structural metadata and context

A digitised 12-page file needs a reliable page order; an audiobook connects chapters and audio segments.

A photograph might have a capture master, an access JPEG and a thumbnail, all belonging to one described item.

Archival records also belong to series and fonds, not merely folders of unrelated scans.

Key point: Preserve meaningful relationships between resources and their parts.

Technical metadata in practice

Images: pixel dimensions, colour space, bit depth and encoding format where needed.

Audio: sample rate, channels, duration, bit depth or codec; video: frame size, frame rate, container and codec.

Record technical facts from reliable file inspection and capture logs; do not guess based on an extension.

Key point: Technical metadata helps render, migrate and evaluate media.

Administrative and rights metadata

Rights information records ownership, licences, restrictions and permission status—not simply “copyrighted”.

Administrative information can record custody, acquisition, responsibility, embargoes and access procedures.

Confidential records require enforceable access controls; an “internal” tag alone does not secure a public web file.

Applied explanation. Rights statements must be supported by a real decision or authority; do not guess that a file is open merely because it was supplied to a student. A discovery catalogue can publicly expose limited descriptive information while storage and access controls keep the sensitive underlying file private. Any such exposure should itself be assessed for personal data risks.

Key point: Describe restrictions accurately and enforce them outside metadata.

Preservation metadata and events

Preservation metadata supports integrity, provenance and long-term management.

A checksum algorithm and value can be stored with a verified date; a later check becomes a recorded event.

PREMIS describes objects, events, agents and rights so actions on digital objects can be interpreted.

Key point: A checksum match supports byte-level fixity, not the truth of descriptive content.

9.2 Standards and Dublin Core

Metadata standards: why interoperability matters

Standards let systems exchange or interpret fields using shared meanings.

A local field “item_description” may map to Dublin Core description for basic exchange.

An institution can adopt a standard plus local rules for scope, required fields, vocabulary and controlled access.

Key point: A standard is a foundation; a useful application profile makes it operational.

Dublin Core: fifteen core elements

Contributor, Coverage, Creator, Date, Description, Format, Identifier, Language, Publisher.

Relation, Rights, Source, Subject, Title and Type complete the original fifteen elements.

These elements are general and repeatable where appropriate; local systems may add more specific refinements.

Applied explanation. The original Dublin Core Metadata Element Set contains fifteen named elements. The broader DCMI Metadata Terms vocabulary supplies more specialised properties such as spatial and temporal coverage, created and modified dates, and relationships. A training record can use an introductory set of fields while a production system defines more precise meanings and validation rules.

Key point: The fifteen elements provide a shared vocabulary, not a complete archival management system.

Dublin Core example: photograph

Title: “Fictional campus library opening”; Creator: Learning Media Lab; Date: 2024-06-12.

Type: StillImage; Format: image/tiff; Subject: Libraries—Orientation; Language: not applicable to a purely visual photo.

Identifier: LIB-PH-004; Rights: classroom demonstration, approved internal use.

Key point: Record only known facts, and keep identifiers consistent across files.

Dublin Core example: archival audio

Title: “Fictional service desk oral history”; Creator: Training Media Team; Date: 2025-02-11.

Type: Sound; Format: audio/wav; Subject: Records services; Language: sw; Identifier: ARC-OH-002.

Relation: ARC-OH-002-transcript; Rights: internal training only; Description: synthetic classroom narration.

Applied explanation. For Sound, the language usually describes spoken content; for a purely visual photograph, a language value may be absent or explicitly not applicable according to a local profile. Avoid inserting “English” merely because the cataloguer wrote an English description. The language of a metadata description is not automatically the language of the resource.

Key point: Media and transcripts should be connected with explicit relationships.

9.3 Identifiers, organisation and context

Choose fit-for-purpose richer standards

MARC 21 supports rich bibliographic cataloguing; EAD is commonly used for archival finding aids.

METS can package descriptive, administrative and structural information for complex digital objects.

PREMIS focuses on preservation actions and entities; none of these should be confused with the fifteen Dublin Core elements.

Key point: Select standards according to the service and interoperability requirements.

Identifiers: unique, stable and meaningful

A local identifier such as LIB-IMG-014 can distinguish an item within an institution.

Separate item identifiers from file names and versions; a format conversion should not silently create a new intellectual item.

Persistent identifier services such as DOIs or ARKs have governance requirements; a local code is not automatically persistent.

Applied explanation. For a locally managed code, first establish scope: item identifiers must be unique within the catalogue and must not be reassigned. A file ID is a separate technical identity and can change after migration. A persistent identifier scheme requires an enduring organisational commitment and, in many cases, a resolver and maintenance policy.

Key point: An identifier is useful only when its uniqueness and resolution are managed.

Design a file naming policy

Example: ARC032_p003_master.tif and ARC032_p003_access.jpg connect page, role and item.

Use predictable characters, consistent zero padding, roles and controlled versioning.

Do not place passwords, private names or sensitive descriptions in public filenames.

Key point: File naming supports management but is not a replacement for a catalogue.

Collection hierarchy and archival context

Example BLISS: collection → exhibition theme → digital item → media file.

Example BRIM: fonds/creating body → series → file → item → digital representation; actual structures vary by institution.

Describe provenance, original order and custody so records are not removed from their evidential context.

Applied explanation. A single scan of a photograph may belong to an item that belongs to a series in an archival fonds. Removing the image from its descriptive context can conceal the creator, series function and restrictions. An archive should preserve original order and provenance where they carry evidential significance; a library may organise discovery around subjects, genres and user needs. Both require stable relationships.

Key point: A search result must lead back to its collection and source context.

Relationships and derivatives

Relation fields connect a master with its access JPEG, thumbnail, caption or OCR text.

Record source identifiers and derivative events so a transformed file remains traceable.

A transcript adds searchable content but should not be mistaken for the entire sound recording.

Key point: Link related files and indicate their different functions.

9.4 Names, dates and controlled terms

Subjects, keywords and controlled vocabularies

Free keywords are flexible, but “student orientation” and “induction” may retrieve different results.

A controlled vocabulary supplies preferred terms, variants and consistent subject labels.

Local Swahili/English subject mappings can improve multilingual discovery if reviewed for meaning.

Applied explanation. Controlled subject terms and authority files are maintained tools. For instance, an authority record might identify the preferred form “Library orientation” and connect it to a synonym “Induction to library services”. The search interface can then expand a query without storing unrelated variants as separate uncontrolled subjects. Swahili–English matches should be checked for semantic equivalence rather than translated automatically and assumed correct.

Key point: Search quality depends on consistent terminology and user language.

Authority control and names

The same creator may appear as “Campus Library”, “Main Campus Library” or an abbreviation.

Maintain a preferred name form, stable authority ID and known alternatives.

Do not merge different people or organisations solely because their names look similar.

Key point: Authority records reduce ambiguity without erasing distinctions.

Dates, languages and missing values

Use an agreed date convention, often ISO 8601 (YYYY-MM-DD) when full dates are known.

Use explicit language codes consistently where appropriate, such as en or sw, after confirming content language.

Unknown is different from an empty field, guessed date or publication date substituted for event date.

Key point: Good metadata preserves uncertainty instead of inventing precision.

9.5 Retrieval and search evaluation

Search: exact matches, text matches and facets

Exact identifier search retrieves a known record; keyword search matches text in selected fields.

Facets let users narrow results by type, subject, date range, language or permitted access.

A query against titles only differs from one against title, description and subject.

Applied explanation. Consider a query for “records”. If the system searches only title it may return the oral-history item but miss a video whose title uses “transfer”; searching descriptions and subjects may return both. Facets can narrow by type, programme and access. An “internal” item should not have a download link simply because it appears in a result list.

Key point: Define what is indexed and how users can filter the results.

Full-text OCR versus catalogue metadata

OCR extracts text from page images and can add useful searchable content.

OCR errors, reading order and low-quality captures can produce false or missed matches.

Metadata describes the whole resource and can remain useful when OCR is absent or unreliable.

Key point: Use OCR as an additional access layer, not a replacement for description.

Precision, recall and relevance

Precision asks: of the returned results, how many are relevant to the query?

Recall asks: of all relevant items in the collection, how many were returned?

A narrow subject search may improve precision but miss synonyms; broader searching can increase recall and noise.

Applied explanation. Suppose there are four relevant items in a collection. A search returns three results and two are relevant. Precision is 2/3 ≈ 66.7%; recall is 2/4 = 50%. A term mapping could increase recall but may also add irrelevant results. The choice depends on the users and their tasks.

Key point: Test with realistic tasks, not only whether the search box returns something.

9.6 Metadata quality, formats and governance

Metadata quality dimensions

Completeness: required fields present; accuracy: facts match sources; consistency: shared rules followed.

Uniqueness: identifiers are not duplicated; timeliness: rights and availability are kept current.

Provenance: contributors, source evidence and revisions can be traced.

Key point: A filled field is not necessarily a correct field.

Quality assurance: review a batch

Validate duplicate item IDs, missing titles, unknown rights states and inconsistent format names.

Review subject terms, impossible dates, broken relations and publication restrictions with human judgement.

Track corrections in an audit log; preserve prior meanings when changes affect record evidence.

Applied explanation. A validator can check empty titles, duplicate identifiers and date patterns, but it cannot prove that the described subject is accurate, that the quoted creator is correct or that rights are resolved. Combine machine checks with source inspection and documented human review. Audit logs should indicate who approved changes, when, and which evidence informed them.

Key point: Automated validation flags problems; people make contextual decisions.

Record structure: CSV and JSON

CSV is convenient for flat tabular metadata; quote commas correctly and use UTF-8 encoding.

JSON can express arrays and nested relationships but still requires an agreed schema.

The schema should say which fields are required, repeatable, controlled, private and displayable.

Applied explanation. The same record can be represented in a CSV row or a JSON object; these serialisation formats do not define the meaning of fields. A well-managed application profile specifies field labels, definitions, required status, repeatability, controlled vocabularies, privacy and example values. Encoding consistency matters for Swahili names and other non-ASCII text.

Key point: A file format is not the same thing as a metadata standard.

Worked example: a catalogue row

ID LIB-IMG-014 | Title “Local history training poster” | Type StillImage | Subject local history.

Creator Training Media Team | Date 2025-01-10 | Rights classroom use | Access public demo.

Related files: LIB-IMG-014_master.tif and LIB-IMG-014_access.jpg; each file has its own technical metadata.

Key point: A complete row names the item and points to its actual files.

Worked example: restricted record

ID ARC-MIN-007 | Title “Fictional committee minutes” | Creator Training Records Office.

Series ARC-MIN | Date 2024-05-17 | Type Text | Rights restricted internal use; access not public.

A public discovery catalogue may show a limited description while the underlying files remain authorised-only.

Applied explanation. The example restricted minutes are entirely fictional. They illustrate that a catalogue might disclose a title and series while restricting content to approved staff. Whether the title itself is safe to expose depends on its content and local policy. Never upload real restricted records to a public teaching site.

Key point: Public discovery and permission to view the content are separate decisions.

Practical workflow: from file to retrieval

1. Inventory; 2. assign stable IDs; 3. capture known fields; 4. identify rights and sensitivity.

5. establish controlled subject terms; 6. connect related files; 7. validate; 8. test search/facets.

9. correct and record changes; 10. publish only approved descriptions and access files.

Key point: A search interface is the visible end of a documented metadata workflow.

Design an application profile

Choose required fields (identifier, title, type, rights/access) and optional fields (creator, date, language, duration).

State accepted values, missing-value rules, name authorities, identifiers and relationship rules.

Include public-display rules and privacy review before exporting metadata.

Key point: An application profile makes a general standard consistent for one institution.

9.7 Applications and practical work

Hands-on retrieval task

Search the fictional eight-record collection by keyword, type and access status.

Compare a subject search against a broad title/description/subject query; record the number of results.

Fix one incorrectly described record and explain how the correction improves retrieval or reduces risk.

Key point: Measure the effect of metadata choices using realistic questions.

BLISS application: library digital collection

Describe a themed set of images, recordings and learning videos with stable titles and subjects.

Connect original media to captions, transcripts and access versions.

Use catalogue facets to help new users find a resource by topic, format, language and audience.

Key point: Organised metadata supports discovery and inclusive information services.

BRIM application: records and archives

Preserve creating body, provenance, record series, original order and record status.

Record relationships between files, page sequences, derivatives and preservation events.

Distinguish discoverable descriptions from protected records; document who approves access.

Key point: Trustworthy retrieval depends on archival context and appropriate controls.

Worked retrieval calculation

Precision and recall

Four resources are relevant. Your search returns three results, of which two are relevant. Precision = 2 ÷ 3 = 66.7%; recall = 2 ÷ 4 = 50%. To improve recall, test synonyms; to improve precision, add subject or type facets. Verify any claimed improvement against a relevance list.

Quality control

Flawed training batch

Download the intentionally flawed metadata CSV. Identify the repeated identifier, a missing title, a non-standard date and an access label that conflicts with the description. Explain which faults a simple script can flag and which require human source or permissions review. Never publish the sensitive file solely because the row says “public”.

9.9 Practice and reflection

  1. Choose a fictional media item and describe it using title, creator, subject, date, type, format, identifier, rights and relation.
  2. Add appropriate technical fields and record their sources. Distinguish item identity from technical file identity.
  3. Use a controlled subject term and one synonym; demonstrate which user query may otherwise fail.
  4. Check a metadata batch for duplicates, blanks, inconsistent dates and suspicious access rules.
  5. Search the training collection using an identifier, a keyword and a facet. Evaluate what each method finds.
  6. Build a BLISS digital-exhibition catalogue or a BRIM series-linked records list and document the resulting decisions in a short report.

Self-check

Could a different student locate the exact item, verify who created it, identify its parent collection, distinguish its master and access copy and know whether they may view it? If any answer is no, identify the missing metadata or governance decision.
